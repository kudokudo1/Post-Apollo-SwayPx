## IMPLEMENTATION

PR #60 showed a native `xdg_popup` that was **not** generated by the Chrome executable. Its 16,000-pixel positive control and zero-pixel same-cgroup negative proved an XDG popup guard, but not multiple browser *top-level windows*.

This test follows the actual browser path. Its fourth independent GitHub Actions matrix job launches Chrome with `--app=about:blank` inside the exact disposable `sd-ci-chrome-wayland-RUN-ATTEMPT.service`. After the initial window is kernel/cgroup-verified and its 320x240 mask screenshot passes, a private 0600 runner request causes the **real `/opt/google/chrome/chrome` executable** to be invoked again, using the **same private profile** with `--new-window about:blank`. The request wrapper runs inside the existing service. It preserves its PrivateNetwork, NoNewPrivileges, ProtectHome, tasks/memory limits and control-group teardown. No developer workstation process or browser profile is touched.

A Python observer requires the original Sway native XDG ID/PID to remain mapped, a second distinct native XDG ID from a kernel-live process in the exact service cgroup, and a Chrome-executable request marker from the service journal. Real grim screenshots and before/after Sway IPC trees are retained. A separate pixel checker samples the real output **outside** the initial clip and records whether any new bright pixels appeared; it also records whether Sway moved the original native view.

The diagnostic returns an explicit **OBSERVED** result with classification `VISIBLE_OUTSIDE_MASK` or `NO_OUTSIDE_BRIGHT_PIXELS`. Neither is a permission grant or general containment verdict: an observed leak must be addressed by a separate fail-closed guard and rerun, not misrepresented as a passing confinement check. Exact service stop and native process/profile/window teardown must succeed.
